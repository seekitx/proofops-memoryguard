# Casework benchmark protocol

## What it measures

Twenty-four independently initialized, authored **synthetic scenarios** compare four policies. Every scenario creates a separate workspace; these are not24 checks against one story. However, independence of fixtures is not statistical independence of a market sample, a held-out corpus, a user study or external evaluation.

Arms:

1. `casework_v2`: the shipped current-memory policy and casework flow.
2. `current_config_no_history`: same current scopes/limits/dependencies, no remembered adverse risk/taint history; it is NOT deliberately denied the baseline configuration.
3. `sticky_adverse_history`: retained adverse history that does not fully model recovery/review semantics.
4. `always_stop`: deliberately conservative boundary case, making false stops visible.

Only arm1 is the product; alternatives are isolated benchmark functions and cannot be selected by runtime configuration.

Scenarios include safe baseline, missing baseline, expiry, tightened/raised cap, dispute, revocation, partial resolution, recovery before/after explicit review, reopen, unrelated scope, dependency depth and prompt-text isolation. Cross-subject isolation, stale-artifact attacks and missing/corrupt memory are additional unit/integration tests, not extra cases silently counted in the24-scenario dataset. Inspect the script for exact expected results; do not claim real-world coverage beyond the authored cases.

## Metrics with denominators

- Hazardous false-READY: expected DENY cases incorrectly receiving READY / all expected DENY cases.
- Benign false-hold: expected READY cases receiving non-READY / all expected READY cases.
- Uncertain false-READY: expected NEEDS_HUMAN cases receiving READY / all such cases.
- Exact verdict accuracy: matching READY/DENY/NEEDS_HUMAN / all scenarios.

No money moves; “false READY” is not a measured unauthorized payment. A zero observed error on a small authored set is not zero real-world risk. This test must not be advertised as measured financial savings, attack success rate across all prompts or PMF.

## Backends

Default `--backend sibyl` opens actual official local SDK workspaces in temporary directories. Missing SDK fails. `--backend test` is an explicit unit-development option and labels its report TEST_DOUBLE_NOT_SIBYL. The generation environment only ran this second mode.

Each report includes source-tree SHA256, backend, Python/runtime metadata, test definitions/results and caveats. Latency is diagnostic: full service persists audit/history while comparator functions do not. Consequently `timing_comparable=false`; do not promote these numbers as fair performance speedups.

## Stronger next experiment

Freeze the public authored test set and final commit. Ask an independent builder to reproduce using official SDK, then contribute additional adversarial cases before a second fixed evaluation. For real utility, collect permissioned operator case-handling time, wrong stops and repeat work on genuine tasks; predefine metrics and report failures. No user data or financial return claim is generated by this bundle.
